# SurgeonPulse mobile app

The participant app for SurgeonPulse. It records a surgeon's heart rate during a case, lets the team mark operative
phases and events, collects a short post-op SURG-TLX debrief, and shows per-session feedback and trends. One
codebase (Expo SDK 58, React Native 0.88, Expo Router) runs on **iOS, Android and the web**.

> **Research tool, not a medical device.** SurgeonPulse does not diagnose anything and does not monitor patient
> safety. Never enter patient names, record numbers or other identifiers anywhere in the app.

## Quick start: web demo

The web build is the fastest way to try the whole flow with the built-in simulator. From the repository root,
install once and start the dev server:

```bash
npm install                 # once, at the repo root (npm workspaces)
cd apps/mobile
npm run web                 # same as: npx expo start --web
```

Then: complete onboarding (use a study code such as `SP-001`), tap **Start new case**, pick a procedure, choose
**Simulator (demo)**, record a short baseline, mark phases and events on the live screen, hold **End case** for
1.5 seconds and fill in the debrief. **Insights → Load demo data** adds 12 simulated sessions to explore trends.

To produce a static site (for a demo server or automated tests):

```bash
npx expo export --platform web --output-dir dist
npx serve -s dist           # any static server with single-page fallback works
```

On the web, sessions and settings are kept in the browser's `localStorage` (about 4 MB budget), so clearing site
data removes them.

## Running on a phone (development build)

Bluetooth (`react-native-ble-plx`), Apple Health (`@kingstinct/react-native-healthkit`) and Health Connect
(`react-native-health-connect`) are native modules that **Expo Go does not include**. In Expo Go the app still runs,
but only the simulator source is available. To use real sensors you need a development build.

`expo-dev-client` is not yet a dependency. Add it once before your first development build:

```bash
cd apps/mobile
npx expo install expo-dev-client
```

### Option A: build in the cloud with EAS (no Xcode or Android Studio needed)

```bash
npx eas-cli@latest login
npx eas-cli@latest init                                         # links the project, adds extra.eas.projectId
npx eas-cli@latest build --profile development --platform android   # APK you can install directly
npx eas-cli@latest build --profile development --platform ios       # register devices first: eas device:create
npx expo start --dev-client                                    # then open the installed app
```

### Option B: build locally

Requires Xcode (macOS, iOS 16.4+ device) or Android Studio (Android 8.0 / API 26+ device).

```bash
npx expo run:ios --device
npx expo run:android --device
```

`ios/` and `android/` are generated by prebuild (Continuous Native Generation) and are git-ignored. Do not edit
them by hand: native settings live in `app.json` and the config plugins it lists (including
`plugins/withOptionalBluetooth.js`). Regenerate them with `npx expo prebuild --clean`.

Bluetooth does not work in the iOS Simulator or most Android emulators, so test sensors on a real device.

## Build profiles (EAS)

`eas.json` defines three profiles:

| Profile | Purpose | Distribution |
| --- | --- | --- |
| `development` | Development client for day-to-day work (`developmentClient: true`) | Internal (Android APK, ad-hoc iOS) |
| `preview` | Release build for pilot participants and the research team | Internal (Android APK, ad-hoc iOS) |
| `production` | Store build; the build number increments automatically (versions are managed remotely by EAS) | App Store / Play Store |

```bash
npx eas-cli@latest build --profile preview --platform all
npx eas-cli@latest build --profile production --platform all
npx eas-cli@latest submit --profile production --platform ios
```

## Heart-rate sources and supported sensors

Choose the source on the **New case** screen, or set a preferred one in **Settings → Heart-rate sensor**.

| Source | iOS | Android | Web | Data |
| --- | --- | --- | --- | --- |
| Bluetooth heart-rate strap | Yes | Yes | Chrome / Edge (Web Bluetooth) | Live HR, plus RR intervals when the sensor sends them |
| Apple Watch (via Apple Health) | Yes | — | — | Imported after the case |
| Smartwatch (via Health Connect) | — | Yes | — | Imported after the case |
| Simulator (demo) | Yes | Yes | Yes | Generated, clearly labelled as simulated |

**Bluetooth sensors.** Any device that implements the standard Bluetooth LE **Heart Rate Profile** (service
`0x180D`) works, for example a Polar H10 chest strap. HRV metrics (RMSSD, SDNN, stress index) need beat-to-beat RR
intervals. Chest straps such as the Polar H10 send them; many optical armbands and watch "broadcast HR" modes send
heart rate only, so those sessions have no HRV. Some straps don't advertise the heart-rate service, so the sensor
screen has a **Show all devices** option. The app reconnects automatically after a dropout (back-off from 1 s up to
30 s) and shows a "Signal lost" banner after 15 s without data.

**Web Bluetooth** needs a Chromium-based browser (Chrome, Edge, Android Chrome) on `https://` or `localhost`. The
browser shows its own device chooser. In Safari and Firefox the Bluetooth option shows as unavailable, and the
simulator still works.

**Apple Health / Health Connect (timed sessions).** For a watch that cannot stream to the phone, start a workout on
the watch, then choose the health-store source. The live screen shows elapsed time and the event buttons only. After
the case, the debrief (**Import heart rate now**) and the session page (**Import from Apple Health / Health Connect**) read heart rate (plus Apple Health
SDNN / heartbeat series, or Health Connect RMSSD) for the session window and recompute the summary. Health Connect
is built into Android 14+. On Android 9–13, install the Health Connect app from the Play Store.

## Permissions

The app asks only for what it uses, at the moment it needs it.

| Platform | Permission | Why |
| --- | --- | --- |
| iOS | `NSBluetoothAlwaysUsageDescription` | Connect to the heart-rate sensor |
| iOS | `UIBackgroundModes: bluetooth-central` | Keep receiving sensor data if the screen locks during a long case |
| iOS | HealthKit entitlement + `NSHealthShareUsageDescription` | Read heart rate and HRV (read-only; the app never writes to Apple Health) |
| Android 12+ | `BLUETOOTH_SCAN` (`neverForLocation`), `BLUETOOTH_CONNECT` | Find and connect to the sensor; scan results are never used for location |
| Android ≤ 11 | `ACCESS_FINE_LOCATION` (max SDK 30) | Required by Android for BLE scanning on these versions |
| Android | `health.READ_HEART_RATE`, `health.READ_HEART_RATE_VARIABILITY` | Health Connect import |
| Android | `INTERNET`, `VIBRATE` | Research upload; haptic confirmation of taps |
| Web | Web Bluetooth device chooser | Granted per device by the user |

The storage and overlay permissions that Expo templates add by default (`READ/WRITE_EXTERNAL_STORAGE`,
`SYSTEM_ALERT_WINDOW`) are blocked in `app.json`, because exports go through the system share sheet. Bluetooth is
declared as an *optional* hardware feature, so the app also installs on devices without BLE (Health Connect and the
simulator still work there).

While recording, the screen is kept awake (`expo-keep-awake`, can be turned off in Settings) because the phone
usually sits on a stand for the whole case.

## Data, privacy and research upload

- **Pseudonymous.** Participants are identified only by a study code (e.g. `SP-014`), checked so that it can't be an
  email address. Procedures come from a catalogue, and free-text fields warn against entering identifiers.
- **Local first.** Data stays on the device: SQLite (`surgeonpulse.db`) on iOS/Android, `localStorage` on the web.
  Signals are saved every 5 s while recording, so a crash loses at most a few seconds, and an interrupted case is
  offered for recovery on the next launch.
- **Exports** (Settings → Data, or a session's actions) are de-identified by default: notes and device ids are
  removed. Formats: SurgeonPulse JSON bundle, per-session CSVs (samples, RR, events) and a one-row-per-session
  summary CSV for SPSS/R/Stata.
- **Research upload.** Enter the study server URL and the enrolment token from the research team in **Settings →
  Research study**, then use **Check enrolment**. Uploads are de-identified, never include demo or in-progress
  sessions, and can run automatically after each debrief. The server URL must use `https://` (plain `http://` is
  accepted only for `localhost` and private LAN addresses during testing). The token is stored only on the device and
  is never logged or exported. See `apps/server/README.md` for running the server and issuing tokens.
- **Withdrawal.** Settings → Privacy & consent → Withdraw consent, and Settings → Data → Delete all data.

## Testing

Run these from `apps/mobile`:

```bash
npx tsc --noEmit                    # type-check (strict)
npx jest                            # unit + component tests (jest-expo, iOS preset)
npx jest --preset jest-expo/android src/components __tests__/ui   # UI tests under the Android preset
npx expo export --platform web      # web bundle must build (no native-only module may reach it)
npx expo config --type public       # app config resolves
CI=1 npx expo prebuild --no-install --clean   # inspect generated native projects, then delete ios/ and android/
npx expo-doctor                     # dependency and config checks
```

**Browser end-to-end flow.** `e2e/web-flow.mjs` drives the exported web build in Chromium at phone size (onboarding →
setup with the simulator → baseline → live screen with phases, a complication marker, the logger toggle and undo →
hold to end → debrief → session detail → Insights with demo data → History → Settings → reload). It also checks the
landscape live screen and fails on console errors or warnings. It uses the `playwright` package already installed at
the repo root for the dashboard.

```bash
npx expo export --platform web --output-dir /tmp/mobile-web
npx serve -s /tmp/mobile-web -l 8090 &
node e2e/web-flow.mjs http://localhost:8090      # screenshots: $SCREENSHOT_DIR (default: OS temp dir)
```

Running the same script against `npx expo start --web` also catches development-only React warnings (missing keys,
invalid props).

The native Bluetooth, HealthKit and Health Connect code is unit-tested with mocks. Before a study, check it on real
devices with a development or preview build: connect a strap, walk out of range and back (reconnect), lock the screen
during recording, and import a watch workout.

## Project layout

```
src/app/          Expo Router screens: onboarding, (tabs)/ Record · History · Insights · Settings,
                  record/ setup → baseline → live → debrief, session/[id], session/events/[id], sensors, about
src/components/   UI primitives and hand-rolled react-native-svg charts
src/hooks/        UI hooks
src/theme/        light / dark / OR-mode tokens
src/services/     sensors (BLE native, Web Bluetooth, simulator), health (HealthKit, Health Connect),
                  storage (SQLite / localStorage), export, upload, platform helpers
src/state/        zustand stores: recording state machine, settings, sessions
plugins/          local Expo config plugins
e2e/              browser end-to-end flow (Playwright)
```

Platform-specific code uses file suffixes (`.native.ts`, `.web.ts`, `.ios.ts`, `.android.ts`), so native-only
modules never reach the web bundle. All analytics, parsing, labels and the simulator come from
[`@surgeonpulse/core`](../../packages/core/SPEC.md). See [`SPEC.md`](SPEC.md) for the app architecture.
