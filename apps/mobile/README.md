# SurgeonPulse mobile app

The participant app for SurgeonPulse. It records a surgeon's heart rate during a case, lets the team mark operative
phases and events, collects a short post-op SURG-TLX debrief, and shows per-session feedback and trends. One
codebase (Expo SDK 58, React Native 0.88, Expo Router) runs on **iOS, Android and the web**.

> **Research tool, not a medical device.** SurgeonPulse does not diagnose anything and does not monitor patient
> safety. Never enter patient names, record numbers or other identifiers anywhere in the app.

## Quick start: web demo

The web build is the fastest way to try the whole flow with the built-in simulator. From the repository root,
install once and start the dev server:

```bash
npm ci                      # once, at the repo root (npm workspaces)
cd apps/mobile
npm run web                 # same as: npx expo start --web
```

Then: complete onboarding (use a study code such as `SP-001`), tap **Start new case**, pick a procedure, choose
**Simulator (demo)**, record a baseline (**Finish early** is available after 60 seconds) or skip it, mark phases and
events on the live screen, hold **End case** for
1.5 seconds and fill in the debrief. **Insights → Load demo data** adds 12 simulated sessions to explore trends.

To produce a static site (for a demo server or automated tests):

```bash
npx expo export --platform web --output-dir dist-web
node e2e/serve-spa.mjs dist-web 8090   # http://127.0.0.1:8090; any static server with a single-page fallback works
```

On the web, sessions and settings are kept in the browser's `localStorage` (about 4 MB budget), so clearing site
data removes them. When the budget is full, the heart-rate data of the oldest finished cases is dropped first (a case
being recorded last), and **History** shows a "Browser storage is full" banner asking you to export all sessions from
Settings before closing the page; until then everything is still in memory.

## Running on a phone (development build)

Bluetooth (`react-native-ble-plx`), Apple Health (`@kingstinct/react-native-healthkit`) and Health Connect
(`react-native-health-connect`) are native modules that **Expo Go does not include**. In Expo Go the app still runs,
but only the simulator source is available. To use real sensors you need a development build.

`expo-dev-client` is already a dependency, so you can make a development build straight away.

### Option A: build in the cloud with EAS (no Xcode or Android Studio needed)

```bash
npx eas-cli@latest login
npx eas-cli@latest init                                         # links the project, adds extra.eas.projectId
npx eas-cli@latest build --profile development --platform android   # APK you can install directly
npx eas-cli@latest build --profile development --platform ios       # register devices first: eas device:create
npx expo start --dev-client                                    # then open the installed app
```

### Option B: build locally

Requires Xcode (macOS, iOS 16.4+ device) or Android Studio (Android 8.0 / API 26+ device).

```bash
npx expo run:ios --device
npx expo run:android --device
```

`ios/` and `android/` are generated by prebuild (Continuous Native Generation) and are git-ignored. Do not edit
them by hand: native settings live in `app.json` and the config plugins it lists (including
`plugins/withOptionalBluetooth.js`). Regenerate them with `npm run native:prebuild` (runs `npx expo prebuild --clean`,
which deletes and recreates both folders).

Bluetooth does not work in the iOS Simulator or most Android emulators, so test sensors on a real device.

## Build profiles (EAS)

`eas.json` defines three profiles:

| Profile | Purpose | Distribution |
| --- | --- | --- |
| `development` | Development client for day-to-day work (`developmentClient: true`) | Internal (Android APK, ad-hoc iOS) |
| `preview` | Release build for pilot participants and the research team | Internal (Android APK, ad-hoc iOS) |
| `production` | Store build; the build number increments automatically (versions are managed remotely by EAS) | App Store / Play Store |

```bash
npx eas-cli@latest build --profile preview --platform all
npx eas-cli@latest build --profile production --platform all
npx eas-cli@latest submit --profile production --platform ios
```

Before building for a study, check two values under `expo.extra` in `app.json`:

- `consentVersion` (currently `PICF-1.0`) is recorded with each participant's consent. Set it to the version of the
  participant information and consent form the HREC approved.
- `researchServerUrl` (empty by default) pre-fills **Study server URL** in **Settings → Research study**, and
  **Forget server and token** returns to it. Participants still enter their own enrolment token. Never put a token in
  `app.json`.

## During a case: live screen and debrief

- **Marking events.** Tap a phase or event button. The **Undo** bar appears inside the heart-rate panel (it never
  covers the buttons) for 10 seconds after each mark. **Minimise** does not restart that time: on return the bar shows
  only for what is left of it. After that, the event can only be corrected once the case has ended, in the session's
  event editor (**Edit events & times**). Hold an event button (or, on the web, **Shift+Enter** / Shift+click) to add a
  short note.
- **Ending the case.** Hold **End case** for 1.5 seconds. On the web, keyboard users hold Space or Enter, and a
  keyboard or assistive-technology activation asks "End the case now?" instead.
- **Heart rate on screen.** Settings → Recording → **Show heart rate on the live screen** (on by default) can hide the
  number from the theatre team; heart rate is still recorded. After 15 s without data the number becomes "--" with
  "No signal · last … bpm" beneath it and a **Signal lost** notice (recording continues), and the sensor pill shows
  "No RR" when the sensor sends heart rate without beat-to-beat intervals.
- **Debrief.** The six SURG-TLX sliders start unanswered (no thumb, "Not rated"). The workload score is saved only
  when all six are rated; saving with some unrated asks first and stores the debrief without workload ratings.
  The optional items (self-rated performance, perceived stress, sleep) also start unanswered and have a **Clear**
  button.
- **Insights** shows your own cases only. Demo and simulator data appear in a separate, labelled view ("Your cases /
  Demo").

## Heart-rate sources and supported sensors

Choose the source on the **New case** screen, or set a preferred one in **Settings → Recording → Heart-rate sensor**.

| Source | iOS | Android | Web | Data |
| --- | --- | --- | --- | --- |
| Bluetooth heart-rate strap | Yes | Yes | Chrome / Edge (Web Bluetooth) | Live HR, plus RR intervals when the sensor sends them |
| Apple Watch (via Apple Health) | Yes | — | — | Imported after the case |
| Smartwatch (via Health Connect) | — | Yes | — | Imported after the case |
| Simulator (demo) | Yes | Yes | Yes | Generated, clearly labelled as simulated |

**Bluetooth sensors.** Any device that implements the standard Bluetooth LE **Heart Rate Profile** (service
`0x180D`) works, for example a Polar H10 chest strap. HRV metrics (RMSSD, SDNN, stress index) need beat-to-beat RR
intervals. Chest straps such as the Polar H10 send them; many optical armbands and watch "broadcast HR" modes send
heart rate only, so those sessions have no HRV. Some straps don't advertise the heart-rate service, so the sensor
screen has a **Show all devices** option. The setup and sensor screens show whether beat-to-beat (RR) data is
arriving. The app reconnects automatically after a dropout (back-off from 1 s up to 30 s; if Bluetooth is switched off
it says so and reconnects once it is back on), shows "Signal lost" after 15 s without data, and re-reads the strap's
battery level every 5 minutes (red below 20 %). Values outside 0–300 bpm and RR intervals outside 0–5000 ms are
dropped as sensor glitches.

**Web Bluetooth** needs Chrome or Edge on a desktop computer, or Chrome on Android, on `https://` or `localhost`. The
browser shows its own device chooser. In Safari and Firefox the Bluetooth option shows as unavailable, and the
simulator still works.

**Apple Health / Health Connect (timed sessions).** For a watch that cannot stream to the phone, start a workout on
the watch, then choose the health-store source. The live screen shows elapsed time and the event buttons only. After
the case, the debrief (**Import heart rate now**) and the session page (**Import from Apple Health / Health Connect**) read heart rate (plus Apple Health
SDNN / heartbeat series, or Health Connect RMSSD) for the session window and recompute the summary. The import is
offered only for cases recorded with the health store as the source, or cases without any heart-rate data: it never
mixes a watch's data into a strap's recording. A session that was already uploaded is marked as not uploaded again (and
re-uploaded when automatic upload is on). Health Connect is built into Android 14+. On Android 9–13, install the Health
Connect app from the Play Store.

## Permissions

The app asks only for what it uses, at the moment it needs it.

| Platform | Permission | Why |
| --- | --- | --- |
| iOS | `NSBluetoothAlwaysUsageDescription` | Connect to the heart-rate sensor |
| iOS | `UIBackgroundModes: bluetooth-central` | Keep receiving sensor data if the screen locks during a long case |
| iOS | HealthKit entitlement + `NSHealthShareUsageDescription` | Read heart rate and HRV (read-only; the app never writes to Apple Health) |
| Android 12+ | `BLUETOOTH_SCAN` (`neverForLocation`), `BLUETOOTH_CONNECT` | Find and connect to the sensor; scan results are never used for location |
| Android ≤ 11 | `ACCESS_FINE_LOCATION` (asked at runtime) and `ACCESS_COARSE_LOCATION`, both declared with max SDK 30; `BLUETOOTH` and `BLUETOOTH_ADMIN` (install-time) | Required by Android for BLE scanning on these versions |
| Android | `health.READ_HEART_RATE`, `health.READ_HEART_RATE_VARIABILITY` | Health Connect import |
| Android | `INTERNET`, `VIBRATE` | Research upload; haptic confirmation of taps |
| Web | Web Bluetooth device chooser | Granted per device by the user |

The storage and overlay permissions that Expo templates add by default (`READ/WRITE_EXTERNAL_STORAGE`,
`SYSTEM_ALERT_WINDOW`) are blocked in `app.json`, because exports go through the system share sheet. Bluetooth is
declared as an *optional* hardware feature, so the app also installs on devices without BLE (Health Connect and the
simulator still work there).

While recording, the screen is kept awake (`expo-keep-awake`, can be turned off in Settings) because the phone
usually sits on a stand for the whole case. On the web the wake lock is requested again whenever the tab becomes
visible. **Android has no background recording service yet:** if the app leaves the foreground or the screen locks,
recording pauses. Everything captured so far is saved at that moment, and on return the live screen shows
"SurgeonPulse was in the background" (and "Signal lost" at once if data stopped). The setup screen and the Keep screen
awake setting remind the team to keep the app open with the screen on.

## Data, privacy and research upload

- **Pseudonymous.** Participants are identified only by a study code (e.g. `SP-014`), checked so that it can't be an
  email address. Procedures come from a catalogue, and free-text fields warn against entering identifiers.
- **Local first.** Data stays on the device: SQLite (`surgeonpulse.db`, with `secure_delete` on every write) on
  iOS/Android, `localStorage` on the web. Signals are saved every 5 s while recording and whenever the app leaves the
  foreground, so a crash loses at most a few seconds, and an interrupted case is offered for recovery on the next
  launch. The debrief is saved only once every captured sample is stored; otherwise it says so and asks you to save
  again (nothing is lost). The case being recorded can't be deleted or event-edited until it has ended.
- **Backups.** Android app backup is turned off (`allowBackup: false`). iOS device and iCloud backups include the
  sessions; Android 12+ device-to-device transfer may copy them.
- **Exports** (Settings → Data, or a session's actions) are de-identified by default: notes and device ids are
  removed, and a typed procedure name that is not in the catalogue becomes "Unspecified procedure" (only the specialty
  is kept). Dates and times are kept. Sessions whose participant code is not a study code are left out and counted.
  Formats: SurgeonPulse JSON bundle, per-session CSVs (samples, RR, events) and a one-row-per-session summary CSV for
  SPSS/R/Stata, which leaves out demo and simulator sessions. Export all skips (and reports) a session that can't be
  read. Importing a file skips sessions already on the device and keeps the local copy.
- **Research upload.** Enter the study server URL and the enrolment token from the research team in **Settings →
  Research study**, then use **Check enrolment**. Uploads are de-identified, never include demo, simulator or
  in-progress sessions, and can run automatically after each debrief. The server URL must use `https://` (plain
  `http://` is accepted only for `localhost` and private LAN addresses during testing). The token is kept in
  `expo-secure-store` (iOS Keychain / Android Keystore, this device only, so a backup cannot carry it to another device); on the web it is in the
  browser's storage under its own key, so use **Delete all data** before leaving a shared computer. It is never logged
  or exported. **Forget server and token** removes both. See the [server README](../server/README.md) for running the
  server and issuing tokens.
- **Withdrawal.** Settings → Privacy & consent → **Withdraw consent** records the withdrawal, turns off automatic upload
  and blocks every further upload; when the study server is configured it also offers to delete your data there
  (`POST /api/v1/me/withdraw`) and then forgets the token. Settings → Data → **Delete all data** removes every session,
  the profile and consent record, the server URL and the token, and restarts onboarding (not possible while a case is
  being recorded).

## Testing

Run these from `apps/mobile`:

```bash
npx tsc --noEmit                    # type-check (strict)
npx jest                            # unit + component tests (jest-expo, iOS preset)
npx jest --preset jest-expo/android src/components __tests__/ui   # UI tests under the Android preset
npx expo export --platform web      # web bundle must build (no native-only module may reach it)
npx expo export --platform ios --platform android   # both Hermes bundles build
npx expo config --type public       # app config resolves
CI=1 npx expo prebuild --no-install --clean   # inspect generated native projects, then delete ios/ and android/
npx expo-doctor                     # dependency and config checks
```

**Browser end-to-end flow.** `e2e/web-flow.mjs` drives the exported web build in Chromium at phone size (onboarding →
setup with the simulator → baseline → live screen with phases, a complication marker, the logger toggle and undo →
hold to end → debrief → session detail → Insights with demo data → History → Settings → reload). It also checks the
landscape live screen and fails on console errors or warnings. It uses the `playwright` package (a dev dependency of
this workspace). CI runs it in the `mobile-web-e2e` job. `e2e/serve-spa.mjs` is a dependency-free
static server with a single-page-app fallback, so nothing extra is downloaded.

```bash
npx playwright install chromium                  # once
npx expo export --platform web --output-dir dist-web
node e2e/serve-spa.mjs dist-web 8090 &
node e2e/web-flow.mjs http://127.0.0.1:8090      # screenshots: $SCREENSHOT_DIR (default: OS temp dir)
```

Running the same script against `npx expo start --web` also catches development-only React warnings (missing keys,
invalid props).

The native Bluetooth, HealthKit and Health Connect code is unit-tested with mocks. Before a study, check it on real
devices with a development or preview build: connect a strap, walk out of range and back (reconnect), lock the screen
during recording (iOS; on Android this pauses recording: expect a gap and the "was in the background" banner), and
import a watch workout.

## Project layout

```
src/app/          Expo Router screens: onboarding, (tabs)/ Record · History · Insights · Settings,
                  record/ setup → baseline → live → debrief, session/[id], session/events/[id], sensors, about
src/components/   UI primitives and hand-rolled react-native-svg charts
src/hooks/        UI hooks
src/theme/        light / dark / OR-mode tokens
src/services/     sensors (BLE native, Web Bluetooth, simulator), health (HealthKit, Health Connect),
                  storage (SQLite / localStorage), export, upload, platform helpers
src/state/        zustand stores: recording state machine, settings, sessions
plugins/          local Expo config plugins
e2e/              browser end-to-end flow (Playwright)
```

Platform-specific code uses file suffixes (`.native.ts`, `.web.ts`, `.ios.ts`, `.android.ts`), so native-only
modules never reach the web bundle. All analytics, parsing, labels and the simulator come from
[`@surgeonpulse/core`](../../packages/core/SPEC.md). See [`SPEC.md`](SPEC.md) for the app architecture.
